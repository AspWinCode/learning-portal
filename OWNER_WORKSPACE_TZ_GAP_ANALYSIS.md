# Сверка ТЗ с текущей реализацией (owner workspace)

Дата сверки: 2026-03-23.

## Короткий вывод

- Базовый модуль задачника **уже реализован**: проекты/подпроекты, контакты, задачи, коммуникации, уведомления, настройки, история, поиск и основные связи между сущностями.
- По части backend API покрыт почти весь рекомендованный набор из ТЗ.
- Основные расхождения — в **информационной архитектуре frontend**: вместо набора отдельных страниц (`/tasks/:id`, `/contacts`, `/contacts/:id`, `/communications`, `/notifications`, `/settings`) используется единая страница `/owner-workspace` с вкладками и модалками.

## Что уже сделано (по ТЗ)

## 1) Две страницы по задачам — есть

1. Классическая страница задач: `/tasks`.
2. Owner workspace (вкладка «Задачи»): `/owner-workspace`.

Маршруты присутствуют в роутинге приложения.

## 2) Основные сущности и связи — реализованы

- Проекты (`owner_workspace_projects`) с иерархией подпроектов (`parent_project_id`).
- Контакты (`owner_workspace_contacts`).
- Задачи (`owner_workspace_tasks`) с полями статуса/приоритета/дедлайна/исполнителя/проекта/контакта/предыдущей задачи.
- Связь проект ↔ контакт (`owner_workspace_project_contacts`).
- Комментарии к задачам, связь задач и сообщений, история изменений, уведомления.

## 3) Задачи: ключевые требования — реализованы

- Создание/редактирование задач.
- Фильтрация, сортировка, поиск.
- Режимы отображения: список / канбан / календарь.
- Массовое изменение задач.
- Завершение задачи с двумя вариантами:
  - «Просто закрыть»;
  - «Закрыть и создать следующую».

## 4) Проекты и подпроекты — реализованы

- CRUD проектов.
- Связь родитель/подпроект.
- Добавление/удаление контактов проекта.
- Работа с участниками проекта.

## 5) Контакты и коммуникации — реализованы

- CRUD контактов.
- Просмотр задач и сообщений контакта.
- Список диалогов/лента сообщений.
- Создание задачи из сообщения и привязка сообщения к существующей задаче.
- Синхронизация сообщений из MAX (`/messages/sync-from-max`).

## 6) Уведомления, настройки, история — реализованы

- Центр уведомлений (получение, отметка прочитанного).
- Пользовательские настройки задачника.
- История изменений (audit log).

## Что частично/не полностью совпадает с ТЗ

## 1) Архитектура экранов frontend отличается от ТЗ

В ТЗ заявлены отдельные страницы:

- `/tasks/:id`
- `/contacts`
- `/contacts/:id`
- `/communications`
- `/notifications`
- `/settings`

Сейчас реализован подход «single workspace page»:

- `/owner-workspace` + вкладки,
- отдельные сущности часто открываются в диалогах/внутри вкладок,
- есть отдельные алиасы только для `/owner-workspace/notifications` и `/owner-workspace/settings`.

Это рабочая реализация, но формально не 1-в-1 с разделом 16.1 ТЗ.

## 2) Карточка задачи как отдельная страница

Карточка задачи реализована как диалог внутри owner workspace, а не как отдельный маршрут `/tasks/:id`.

## 3) Каналы уведомлений

Внутрисистемные уведомления есть. Email/push в ТЗ отмечены как опциональные, явной реализации в owner workspace не видно.

## Что ещё сделать, чтобы закрыть ТЗ «буквально»

1. Добавить отдельные маршруты страниц:
   - `/tasks/:id`
   - `/contacts`
   - `/contacts/:id`
   - `/communications`
   - `/notifications`
   - `/settings`
2. Вынести карточку задачи из модалки в полноценную страницу (или сделать гибрид: deep-link + страница).
3. Зафиксировать в документации, что выбран подход «единая рабочая область», если команда осознанно не хочет дробить интерфейс.
4. (Опционально) добавить email/web-push уведомления.

## Практический статус по этапам из ТЗ

- Этап 1 (база): **выполнен**.
- Этап 2 (коммуникации/MAX): **выполнен в базовом варианте**.
- Этап 3 (автоматизация и улучшения): **выполнен частично** (история/массовые действия/настройки есть; расширенную аналитику можно наращивать).
