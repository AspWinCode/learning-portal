## Что нужно добавить или изменить (без поломки БД)

### 1. Причины отсутствия (п. 3.1–3.2 ТЗ)

- **Сейчас:** только `attended` (bool) и `late` (bool). При `attended=false` создаётся пропуск и **не** списывается занятие (уже так).
- **Нужно:** тренер выбирает статус: **Был / Не был / Болел / Олимпиада / Мероприятие / Другое** (с комментарием).
- **Изменения:** в `lesson_attendance` добавить `absence_reason` (string), `absence_comment` (text). В сохранении посещаемости: при причине ≠ «Был» — не списывать, создавать пропуск с причиной. В `absence_follow_ups` хранить причину (для списка менеджера).

### 2. Отработки: назначение и «не пришёл» (п. 4–6)

- **Сейчас:** этапы missed → assigned → made_up / missed_makeup есть, но нет привязки «на какую группу/занятие назначена отработка».
- **Нужно:** при «Подобрать отработку» — предложения по правилам совместимости программ; «Назначить» — зафиксировать группу и дату; «Не пришёл» — вернуть в очередь (переназначить).
- **Изменения:** в `absence_follow_ups` добавить `makeup_group_id`, `makeup_lesson_date`. API: подбор вариантов отработки (по программе ученика и матрице совместимости), PATCH назначения, PATCH «не пришёл» (stage → missed_makeup, сброс назначения).

### 3. Совместимость программ для отработок (п. 5.3)

- **Сейчас:** группы имеют `direction` (first_step, specialist, expert, backend, frontend, oge, ege); ученик — `student_programs` (Program).
- **Нужно:** конфигурируемая матрица: Первый шаг только с Первым шагом; ОГЭ не участвует; Специалист/Эксперт/Backend/Frontend — взаимозаменяемы по правилам.
- **Изменения:** таблица `program_makeup_compatibility` (source_program_id, target_program_id) или настройка по direction; сервис подбора занятий по ученику (программа ученика → совместимые группы → ближайшие даты 14–30 дней).

### 4. Период обучения и дата следующей оплаты (п. 2.2, 8.2)

- **Сейчас:** нет явного «периода» и «даты следующей оплаты».
- **Нужно:** персональный цикл от даты старта/оплаты; дата следующей оплаты; менеджер видит долги и даты.
- **Изменения:** в `student_cards` (или student) добавить `learning_period_start`, `next_payment_date`. При пополнении (ручном/Точка) обновлять `next_payment_date` (например +1 месяц или по абонементу). API для менеджера: список учеников с датой оплаты и статусом.

### 5. Заморозка абонемента (п. 7)

- **Сейчас:** нет.
- **Нужно:** только Owner ставит заморозку (дата начала, окончания); сдвиг периода; тренер видит «Заморожен с … по …»; в период заморозки не требовать отработок; авторазморозка.
- **Изменения:** таблица `student_freezes` (student_id, freeze_start, freeze_end) или поля на карточке. API: owner создаёт/удаляет заморозку; при отображении занятий проверять заморозку и сдвигать next_payment_date при постановке.

### 6. Просрочка оплаты — автозадачи (п. 8.3)

- **Сейчас:** задач по просрочке нет.
- **Нужно:** если через 3 дня после даты начала нового периода/оплаты нет оплаты — создать задачу менеджеру; повторять каждые 7 дней.
- **Изменения:** периодическая задача (scheduler): по ученикам с `next_payment_date + 3 < today` и без оплаты в периоде — создавать Task (тип «оплата просрочена»), при повторении — раз в 7 дней.

### 7. Закрытие «с оплатой по факту» (п. 9)

- **Сейчас:** нет.
- **Нужно:** только Owner; кнопка «Закрыть с оплатой по факту»: показать N посещённых занятий в текущем периоде, сумма = цена/8*N; после фиксации — закрыть ученика, снять незакрытые пропуски/отработки по периоду.
- **Изменения:** API (owner): расчёт N и суммы; подтверждение → запись оплаты (или отдельный тип операции), архивирование ученика/карточки, обновление стадий пропусков (закрыты/не в очереди).

### 8. Роли и права (п. 1)

- Тренер: не видит оплату, долги — **проверить UI** (скрыть счета/балансы для роли trainer).
- Менеджер: не может ставить заморозку и закрывать «по факту» — **проверять в API** (только owner для freeze и close-by-fact).
- Owner: заморозка, закрытие по факту — **реализовать в API**.

## План реализации (по шагам, без поломки БД)

1. **Миграция 0036** (только добавление):  
   - `lesson_attendance`: `absence_reason`, `absence_comment`  
   - `absence_follow_ups`: `makeup_group_id`, `makeup_lesson_date`, `absence_reason`, `absence_comment`  
   - `student_cards`: `learning_period_start`, `next_payment_date`  
   - таблица `student_freezes` (student_id, freeze_start, freeze_end)  
   - таблица `program_makeup_compatibility` (source_program_id, target_program_id) + сиды по правилам WinCode  

2. **Посещаемость:** расширить схему и сохранение: причина + комментарий; при причине ≠ «Был» — не списывать, создавать пропуск с причиной.

3. **API пропусков:** в ответ добавить reason, program; эндпоинты подбора отработок и назначения (makeup_group_id, makeup_lesson_date); «не пришёл» → stage missed_makeup, сброс назначения.

4. **Сервис совместимости:** по student_id → программа ученика → совместимые program_id → группы с расписанием → ближайшие даты 14–30 дней.

5. **Период/оплата:** при пополнении обновлять `next_payment_date`; API «долги/оплаты» для менеджера (список с датой и статусом).

6. **Заморозка:** API owner: создать/удалить заморозку; сдвиг периода при создании; отдача тренеру «заморожен с … по …».

7. **Закрытие по факту:** API owner: расчёт N и суммы, подтверждение, закрытие ученика и пропусков.

8. **Автозадачи просрочки:** scheduler: создание Task при просрочке 3 дня, повтор каждые 7 дней.

9. **Фронт:** журнал тренера — причины отсутствия, бейдж заморозки; менеджер — пропуски, подбор/назначение отработок, долги; owner — заморозка, закрытие по факту.

## Что уже сделано (первая очередь)

- **Миграция 0036:** `lesson_attendance.absence_reason`, `absence_comment`; `absence_follow_ups.makeup_group_id`, `makeup_lesson_date`, `absence_reason`, `absence_comment`; `student_cards.learning_period_start`, `next_payment_date`; таблицы `student_freezes`, `program_makeup_compatibility`.
- **Посещаемость:** тренер передаёт `absence_reason` (was / not_was / sick / olympiad / event / other) и `absence_comment`. Списание только если «Был»; при любой другой причине — пропуск без списания, запись в очередь с причиной.
- **Пропуски API:** в ответ добавлены `absence_reason`, `absence_comment`, `program_name`, `makeup_group_id`, `makeup_lesson_date`, `makeup_group_name`. PATCH при `stage=missed_makeup` сбрасывает назначение отработки.
- **Отработки:** `POST /api/sales/absences/{id}/assign-makeup` (назначить группу и дату), `GET /api/sales/absences/{id}/suggest-makeups` (подбор по совместимости программ). Матрица `program_makeup_compatibility` — заполняется вручную или сидом (ОГЭ исключить, Первый шаг отдельно и т.д.).
- **Заморозка (owner):** `GET/POST/DELETE /api/sales/students/{id}/freezes`. При создании заморозки сдвигается `next_payment_date` на длительность заморозки.
- **Закрытие по факту (owner):** `GET .../close-by-fact-preview` (N занятий, сумма), `POST .../close-by-fact` с `confirm: true` — начисление, архив ученика и карточки, пропуски переведены в made_up.

**Сделано дополнительно:**  
- Автозадачи просрочки оплаты: раз в день планировщик создаёт задачи менеджеру по ученикам с `next_payment_date + 3` дня в прошлом (без дубля в последние 7 дней). Сервис `app/services/payment_overdue_tasks.py`.  
- При пополнении (ручное и Точка Банк) обновляются `learning_period_start` и `next_payment_date` на карточке (`app/services/student_card_period.py`).  
- Фронт: журнал тренера — выбор причины отсутствия (Был / Не был / Болел / Олимпиада / Мероприятие / Другое + комментарий), отображение «Заморожен с … по …»; страница пропусков — причина, программа, кнопки «Подобрать отработку» и «Назначить», «Не пришёл»; в карточке ученика для owner — блок заморозки (добавить/снять) и «Закрыть с оплатой по факту» (предпросмотр + подтверждение).

**Совместимость программ (п.5.3):**  
- Миграция **0037_seed_program_makeup_compatibility**: сид по названиям программ — «ОГЭ»/«оге» исключены, «Первый шаг»/«first» только с собой, остальные — взаимно.  
- API: **GET/POST/DELETE** `/api/sales/program-makeup-compatibility` (owner/admin): просмотр и управление правилами.  
- Страница **Продажи → Совместимость программ (отработки)** (`/sales/program-makeup`): таблица правил, форма «Программа (ученик) → может отрабатывать в → Программа (группа)», кнопка «Добавить» и «Удалить».

## Дополнительно сделано (финальные правки)

- **Тренер не видит финансы (п.1.1):** тренер исключён из доступа к блоку «Счета» в карточке ученика и на странице учеников; в API пополнение счёта разрешено только admin, owner, sales, родитель (тренер не может пополнять).
- **Занятие в период заморозки (п.7.3):** если дата занятия попадает в период заморозки ученика, запись в очередь пропусков (AbsenceFollowUp) не создаётся — отработка не требуется.
